# CalendarServer — описание архитектуры и реализации

Документ описывает внутреннее устройство сервера синхронизации: из чего он
собран, как хранит данные и как устроены обмен записями и общие календари.
Сборка, запуск и администрирование — в [README.md](README.md), рабочие заметки
для агента — в [CLAUDE.md](CLAUDE.md).

Устройство планера здесь не описывается — оно в его собственном `DesDoc.md`
([Calendar](https://github.com/SayxZero/Calendar)). Отсюда планер виден только
снаружи: какие запросы он шлёт и что ждёт в ответ (раздел 10). Как обе части
работают вместе, целиком описано в `DESDOC.md` зонтичного репозитория
[CosmosCalendar](https://github.com/SayxZero/CosmosCalendar).

## 1. Назначение и границы

Сервер держит аккаунты и записи их планеров и раздаёт каждому устройству то,
чего у него ещё нет. Он же ведёт общие календари: кто кому открыл календарь, с
каким правом, какие ссылки выданы, и разводит правку общей записи по всем, кто
календарь делит.

Сознательные ограничения, из которых следует остальная конструкция:

- **Записи непрозрачны.** Для сервера запись — JSON-объект с видом,
  идентификатором и моментом последнего изменения. Что внутри, он не знает и
  знать не должен: новый вид записи в планере не требует правки сервера.
  Единственное исключение — поле `calendarId` записей общего календаря (раздел 6).
- **Конфликты решает время.** Из двух версий записи остаётся более поздняя по
  моменту, который поставило устройство; слияния полей нет. В общем календаре
  к этому добавляются права и явный ответ о том, что применить не вышло.
- **Один поток, одна база.** Сервер однопоточный: запросы обрабатываются по
  одному, каждый обмен — одна транзакция SQLite. Для домашнего сервера на
  несколько устройств этого хватает с запасом, а порядок применения правок
  получается сам собой.
- **Только Qt Core, Network и Sql.** Никакого GUI, никаких сторонних библиотек,
  и даже без модуля QtHttpServer (раздел 3) — сервер собирается из пакетов
  любого современного дистрибутива Linux.
- **HTTP без TLS.** Шифрование — дело обратного прокси перед сервером (nginx,
  Caddy), если сервер выставлен в интернет.

## 2. Устройство проекта

```
            main.cpp                (параметры, администрирование, цикл событий)
               │
     ┌─────────┼──────────┐
     ▼         ▼          ▼
 config.*   httpserver.*  api.*     (JSON API: маршруты, вход, ключи)
                            │
                            ▼
                        storage.*   (SQLite: аккаунты, ключи, записи, обмен)
                            │
                            ▼
                        shares.*    (общие календари: доступ, ссылки, разводка)
```

| Файл | Содержимое | Зависит от |
|---|---|---|
| `src/config.*` | `ServerConfig` — настройки из INI и командной строки, путь к базе | QtCore |
| `src/httpserver.*` | `HttpServer`, `HttpRequest`, `HttpResponse` — HTTP/1.1 поверх `QTcpServer` | QtNetwork |
| `src/api.*` | `Api` — разбор JSON, маршруты, пароли, ключи сеансов, защита от подбора | `storage`, `config`, `httpserver` |
| `src/storage.*` | `Storage` — схема SQLite, аккаунты, ключи, записи, `sync()` | `shares`, QtSql |
| `src/shares.*` | `ShareStore` — общие календари, ссылки, разводка правок | QtSql |
| `src/main.cpp` | разбор параметров, команды `--list-users` и др., консоль в UTF-8, сигналы | всё |
| `tests/tst_server.cpp` | тесты: сервер в процессе, настоящие HTTP-запросы | всё, кроме `main.cpp` |

`CMakeLists.txt` собирает сервер и тесты из одного списка `SERVER_CORE_SOURCES`
(всё, кроме `main.cpp`); `CalendarServer.pro` описывает ту же программу для
qmake и перечисляет файлы руками — новый файл добавляется в оба.

## 3. HTTP (`HttpServer`)

Свой маленький HTTP/1.1-сервер на `QTcpServer`, а не модуль QtHttpServer: того
нет в пакетах Qt большинства дистрибутивов Linux, и его API менялся между 6.4
и 6.8. Планеру нужно немного, и ровно это сервер умеет:

- **постоянные соединения** (`Connection: keep-alive` по умолчанию,
  `Connection: close` закрывает после ответа) и **конвейер**: несколько
  запросов подряд в одном пакете разбираются из буфера соединения по очереди,
  и ответы уходят в том же порядке;
- **тело только с `Content-Length`**; любой `Transfer-Encoding`, кроме
  `identity`, — 501;
- **пределы**: заголовок до 32 КБ (иначе 431), тело — до `max_body_mb`
  (64 МБ, иначе 413: столько весит весь планер одного пользователя в одном
  обмене), не больше 512 соединений, соединение без данных 60 секунд
  закрывается;
- неразборчивый запрос — 400, после ответа на ошибку разбора соединение
  закрывается: где в буфере начинается следующий запрос, уже не понять;
- адрес клиента вида `::ffff:a.b.c.d` (IPv4 через двойной стек) приводится к
  обычному IPv4 — по нему считаются неудачные входы.

Обработчик один (`setHandler`), его ставит `main.cpp`: `Api::handle()`.

## 4. API (`Api`)

### 4.1 Маршруты и ответы

`Api::handle()` разбирает путь (без завершающего `/`) и метод. `GET /` и
`GET /api/ping` отвечают без аккаунта, `register` и `login` — тоже; всё
остальное под `/api/` требует `Authorization: Bearer <ключ>`, иначе 401
`unauthorized`. Не тот метод у этих трёх — 405; у остальных маршрут — это путь
вместе с методом, так что неизвестный путь и не тот метод одинаково дают 404
`not_found`. `HEAD` отвечает как `GET`, без тела.

Ответ всегда JSON. Ошибка — `{"error": "<код>", "message": "<по-русски>"}`:
код стабилен и предназначен программе, текст — человеку, планер показывает
его как есть. Каждый запрос пишется строкой журнала: адрес клиента, метод,
путь, код и время обработки.

`ping` сообщает `service: "calendar-planner-server"` (по нему планер отличает
свой сервер от чужого на том же порту), версию сервера, версию API
(`Api::apiVersion()`, сейчас 1), время и открыта ли регистрация.

### 4.2 Аккаунты, пароли, ключи

- **Логин** — от 3 до 64 символов из латиницы, цифр и `._@-`; хранится как
  введён и отдельно в нижнем регистре (`login_key`) — по нему и ищется, так
  что `Anna` и `anna` — один аккаунт. **Пароль** — от 6 до 256 символов.
- **Пароль** хранится строкой `pbkdf2-sha256$<раунды>$<соль>$<хеш>`:
  PBKDF2-HMAC-SHA256, 120 000 раундов, случайная соль. Раунды записаны в самой
  строке, поэтому их можно поднять, не ломая старые пароли. Сравнение хешей —
  за постоянное время.
- **Ключ сеанса** — 32 случайных байта в base64url. Устройство получает его
  при регистрации и входе; на сервере лежит только SHA-256 ключа (таблица
  `tokens`), и украденная база не даёт войти. Каждое использование ставит
  отметку `last_used_at`; ключ, которым не пользовались `token_lifetime_days`
  (365 дней), удаляется при следующей попытке им войти.
- **Смена пароля** закрывает все сеансы аккаунта, кроме того, из которого её
  сделали; `--set-password` с консоли — все.
- **Защита от подбора.** Неверный пароль при входе и при смене пароля
  записывается за адресом клиента; десять таких за последние десять минут —
  и вход с этого адреса отвечает 429 `throttled`, пока старые попытки не
  выйдут из окна. Счётчик живёт в памяти и при перезапуске сбрасывается.
- `--no-registration` (`allow_registration=false`) закрывает `register`, вход
  в существующие аккаунты остаётся.

### 4.3 Обмен: что проверяется на входе

`POST /api/sync` несёт `since` (курсор устройства), необязательное имя
устройства и массив `changes`. Каждое изменение проверяется до того, как
что-то пишется: вид — `^[a-z_]{1,32}$`, идентификатор — непустой и не длиннее
200 символов, `modified` — больше нуля, у неудалённой записи `data` —
JSON-объект. Одно негодное
изменение отклоняет весь запрос с 400 `invalid`: половина пачки, записанная
без второй, хуже, чем ничего. Признак `restore` (раздел 6.5) читается здесь же.

Дальше всё делает `Storage::sync()` (раздел 5.3), а `Api::sync()` превращает
результат в ответ: `revision`, счётчики `accepted` и `rejected`, `conflicts` и
`changes` — записи, которых у устройства нет.

`GET /api/record?kind=…&id=…` отдаёт одну запись аккаунта как она есть, вместе
с удалённой (`found`, `change` с `deleted`, `modified`, `revision`, `data`).
Курсор устройства тут не участвует и не двигается: это запрос планера,
который собирается править запись и хочет её последнюю версию, не дожидаясь
полного обмена.

## 5. Хранилище (`Storage`)

### 5.1 База

Один файл SQLite `server.db` в папке данных (`ServerConfig::databasePath()`:
`--data-dir`, `data_dir` из INI относительно самого файла, иначе папка данных
пользователя). `PRAGMA journal_mode = WAL` — читатели не мешают записи,
`foreign_keys = ON` — удаление аккаунта уносит каскадом его ключи, записи и
общие календари. При закрытии `wal_checkpoint(TRUNCATE)` переносит журнал в
сам файл, поэтому копия `server.db` остановленного сервера полна.

Все обращения к базе идут из одного потока, на одном соединении; у
`ShareStore` своя ручка того же соединения, и она отпускается раньше, чем
соединение закрывается (`Storage::close()`).

### 5.2 Схема

Версия — в `PRAGMA user_version`, сейчас 2. Все таблицы создаются через
`CREATE TABLE IF NOT EXISTS`, так что файл версии 1 дотягивается сам:
версия 2 добавила только новые таблицы общих календарей.

| Таблица | Колонки | Что это |
|---|---|---|
| `users` | `id`, `login`, `login_key` (уникальный), `display_name`, `password_hash`, `created_at`, `revision` | аккаунты; `revision` — номер последнего изменения этого аккаунта |
| `tokens` | `token_hash` (ключ), `user_id`, `device`, `created_at`, `last_used_at` | сеансы устройств |
| `records` | `user_id`, `kind`, `id` (вместе — ключ), `data`, `deleted`, `modified`, `revision`, `device` | записи планеров; удалённая запись остаётся надгробием с пустым `data` |
| `shares` | `id`, `owner_id`, `calendar_id`, `mode`, `enabled`, `created_at`; уникальны (`owner_id`, `calendar_id`) | открытые календари |
| `share_members` | `share_id`, `user_id` (вместе — ключ), `access`, `twin_id`, `joined_at` | участники и их права |
| `share_links` | `token_hash` (ключ), `share_id`, `single_use`, `expires_at`, `spent`, `created_at` | выданные ссылки |

Индексы: `records(user_id, revision)` — для выборки «что изменилось после
курсора», `tokens(user_id)`, `share_members(user_id, twin_id)` — найти общий
календарь по близнецу участника, `shares(owner_id)`.

### 5.3 Обмен (`Storage::sync()`)

Ревизия — свой счётчик у каждого аккаунта (`users.revision`), а не общий у
сервера: устройству нужен только порядок изменений своего аккаунта, и чужие
обмены его курсор не двигают.

Весь обмен — одна транзакция:

1. Изменения применяются **в том порядке, в котором пришли.** Для общего
   календаря это и есть очередь правок: следующее изменение уже видит
   результат предыдущего.
2. Для каждого изменения сначала спрашивается общий доступ
   (`ShareStore::routeFor()`, раздел 6.3): принадлежит ли запись общему
   календарю и может ли отправитель её менять. Отказ — конфликт `read_only`,
   а сохранённая версия уходит обратно. Правка записи, которую владелец уже
   удалил, — конфликт `deleted` (раздел 6.5).
3. Только потом — правило «побеждает более поздняя»: если сохранённая версия
   новее (`modified` больше), изменение отклоняется, а сохранённая версия
   уходит устройству.
4. Принятое пишется с ревизией `revision + 1` (`INSERT OR REPLACE`), и если
   запись общая, `ShareStore::fanOut()` раскладывает её копии остальным
   (раздел 6.4) — в той же транзакции.
5. В конце `users.revision` поднимается до последней выданной ревизии.

После фиксации собирается ответ: все записи аккаунта с ревизией больше
`since`, кроме только что принятых от этого же устройства — у него они уже
есть, — и плюс отклонённые, в их сохранённой версии. Устройству, которое
синхронизируется впервые (`since = 0`), надгробия не отправляются: удалять ему
нечего. Новый курсор — текущая ревизия аккаунта.

Ошибка SQLite на любом шаге откатывает весь обмен и отвечает 500 `storage`;
устройство повторит его целиком, с тем же журналом.

## 6. Общие календари (`ShareStore`)

### 6.1 Модель

Владелец открывает **свой** календарь — запись вида `calendar` его аккаунта.
`shares` хранит только то, кому он виден: сам календарь остаётся обычной
записью владельца. Режим (`mode`): `read` и `edit` держат всех участников на
одном праве, `custom` позволяет раздать права по одному
(`setMemberAccess()`). Смена режима на `read` или `edit` переписывает права всех участников разом
и, как и правка одного права, сообщает каждому через его близнеца (6.4).

Участник получает **календарь-близнец** — запись `calendar` уже своего
аккаунта, со своим идентификатором (`twin_id`), названием и цветом. Записи
общего календаря у каждого лежат в своём наборе `records`, и в каждой
`calendarId` — тот, которым календарь зовётся у этого человека. Поэтому
устройство участника обменивается только со своим аккаунтом, ровно как без
общих календарей: отдельного протокола для них нет.

Через общий календарь ходят только виды, живущие в календаре:
`event`, `task`, `completion` (`ShareStore::travels()`). Привычки, мелодии,
напоминания сами по себе, выключенные будильники — дело своего аккаунта.

### 6.2 Ссылки

Попасть в календарь можно только по ссылке владельца
(`POST /api/share/link`): токен из системного генератора, в базе — только его
SHA-256, как у ключа сеанса. Ссылка бывает одноразовой (гаснет после первого
перехода — `spent`) или многоразовой, со сроком до года или бессрочной
(`expires_at = 0`). `resolveLink()` отвечает, почему ссылка не работает: её
нет, она использована, срок истёк, доступ закрыт.

`GET /api/share/peek` показывает, куда ведёт ссылка, до присоединения:
календарь владельца как он есть (название, цвет) — с них планер участника
начинает близнеца. О календаре сервер отвечает только владельцу и тем, кого
тот уже впустил; посторонний, не имея ссылки, его не увидит.

### 6.3 Маршрут изменения (`routeFor()`)

Календарь записи берётся из её `data` (`calendarId`), а у удаления, где
данных нет, — из сохранённой версии. Если это календарь отправителя, открытый
хоть кому-то, — отправитель владелец и может всё. Если это близнец
отправителя (`share_members.twin_id`), — отправитель участник, и правка
разрешена только при праве `edit`. Иначе запись не общая, и правило одно:
«побеждает более поздняя».

### 6.4 Разводка (`fanOut()`, `putCopy()`)

Принятая правка общей записи пишется всем, кто делит календарь, кроме
отправителя (его набор уже записан): владельцу — с его `calendarId`, каждому
участнику — с его `twin_id` (`withCalendar()`). Копия получает следующую
ревизию **получателя**, поэтому до его устройств её доносит их обычный обмен.
Владелец пишется первым: правка участника доходит до остальных участников
через оригинал.

`withCalendar()` — единственное место, где сервер разбирает и собирает JSON
записи. Объект `calendar` владельца участникам не отправляется никогда:
название и цвет у каждого свои.

Право участника хранится в `share_members`, но планер участника видит только
свои записи. Поэтому `publishTwinAccess()` переписывает поле `access` прямо в
записи его близнеца (новой ревизией) — и новое право приезжает тем же
обменом. Без этого повышение прав осталось бы в таблице, а планер участника
до конца считал бы календарь доступным лишь на чтение.

### 6.5 Конфликты

Что применить не вышло, возвращается списком `conflicts`, а не молчанием.
Каждый конфликт несёт вид, идентификатор, `calendarId` в написании отправителя,
причину и саму правку — чтобы планеру было что вернуть:

- `read_only` — у участника только чтение. Сохранённая версия уходит обратно,
  правка не записана.
- `deleted` — участник правит запись, которую владелец уже удалил. Правка не
  записана; планер спрашивает, вернуть ли запись. «Вернуть» присылает её ещё
  раз с `"restore": true` — с этим признаком проверка пропускается, и запись
  возвращается к владельцу и остальным. Без признака сервер снова увидел бы у
  владельца удалённую запись и отказал бы, и вопрос повторялся бы без конца.

Обе проверки стоят **раньше** правила «побеждает более поздняя»: это вопросы
пользователю, а правило молчит. Иначе участник, правивший запись без сети,
терял бы работу без единого слова — удаление владельца пришло бы позже и
просто выиграло.

### 6.6 Присоединение и уход

`join()` проверяет ссылку (по ссылке на собственный календарь владелец не
войдёт: `peek` отвечает ему 409 `own_calendar`, `join` — отказом), вписывает участника в `share_members` с правом по режиму и копирует **всё
содержимое календаря** в записи участника с его `twin_id`. Ближайший обычный
обмен приносит календарь на устройство целиком. Второй переход по другой
ссылке на тот же календарь оставляет прежнего близнеца, а не заводит ещё
одного. Одноразовая ссылка гасится только после успешного присоединения.

Уход (`POST /api/share/leave`) и исключение владельцем (`remove` в
`/api/share/member`) — одно и то же с двух сторон: `dropCopies()` ставит на
копиях участника надгробия, чтобы их удалили и другие его устройства, и
участник вычёркивается из списка.

## 7. Настройки (`ServerConfig`)

Сначала читается INI-файл (`--config`, группа `[server]`, пример —
`deploy/server.ini.example`), потом поверх него — командная строка.

| Ключ INI | Параметр | По умолчанию |
|---|---|---|
| `host` | `--host` | все адреса |
| `port` | `-p`, `--port` | 8765 |
| `data_dir` | `-d`, `--data-dir` | папка данных пользователя (`QStandardPaths`) |
| `allow_registration` | `--no-registration` | открыта |
| `max_body_mb` | — | 64 |
| `token_lifetime_days` | — | 365 |

`passwordIterations` в файл не выведено: его понижают только тесты, которым
нужно хешировать много паролей быстро.

## 8. Запуск и консоль (`main.cpp`)

- Команды администрирования (`--list-users`, `--delete-user`,
  `--set-password`) открывают ту же базу, делают своё и выходят, порт не
  занимают — поэтому работают и рядом с запущенным сервером. Пароль
  `--set-password` читается строкой из stdin, так что его можно передать и
  конвейером.
- На Windows консоль переводится в UTF-8 (`SetConsoleOutputCP`), а сообщения
  Qt идут через свой обработчик в UTF-8 с отметкой времени: иначе русский
  текст выходил кашей в ANSI-кодировке. Справку и ошибки разбора параметров
  сервер печатает сам — `QCommandLineParser::process()` печатал бы их так же
  криво.
- Ctrl+C и SIGTERM (systemd) завершают цикл событий: сервер закрывает порт и
  базу, сбросив журнал WAL.
- При старте печатаются версия, порт, путь к базе, открыта ли регистрация и
  адреса машины, по которым к серверу можно подключиться, — с именами сетевых
  интерфейсов. Этот адрес вводят в планере.

`run-server.bat` (Windows) держит сервер в своём окне и отказывается
поднимать второй экземпляр на том же порту и с той же папкой данных.

## 9. Тестирование

`tests/tst_server.cpp` — 22 теста на QtTest. Каждый поднимает `Api` и
`HttpServer` внутри процесса на свободном порту, с базой во временной папке и
пониженным числом раундов PBKDF2, и говорит с ним настоящими HTTP-запросами
через `QNetworkAccessManager`, а конвейер и некорректный HTTP — сырым
`QTcpSocket`:

- **основа** — `ping`, регистрация и вход, отказ на неверный логин, пароль и
  ввод, запросы без ключа, закрытая регистрация;
- **обмен** — передача записей между двумя устройствами, одна запись по
  `/api/record`, «побеждает более поздняя», удаления и надгробия;
- **сеансы** — выход закрывает ключ, смена пароля выводит остальные
  устройства, блокировка подбора;
- **HTTP** — конвейер запросов в одном пакете, разбор некорректного HTTP;
- **общие календари** (восемь тестов) — путь записи до участника, отказ в
  правке при доступе на чтение, повышение прав и его приезд к участнику,
  правка удалённой записи и вопрос о ней, правка без сети, которую не должно
  съесть более позднее удаление, возврат по `restore`, уход с копиями,
  правила ссылок.

Со стороны планера связку проверяет его тест `syncServiceTalksToRealServer`
против запущенного сервера (раздел 10).

## 10. Взаимодействие с планером

Сервер ничего не знает о планере, кроме формы запросов, но планер на кое-что
рассчитывает:

- **Формат записи — дело планера.** `data` — это JSON записи в формате его
  резервной копии; сервер хранит его байтами и отдаёт как есть. Новый вид или
  новое поле в планере сервера не касаются.
- **Момент `modified` ставит устройство.** Сервер ему доверяет и сравнивает
  только между версиями одной записи.
- **Курсор** — `revision` из ответа, устройство присылает его в `since`
  следующего обмена. Устройство с курсором 0 получает весь аккаунт без
  надгробий.
- **`/api/record` перед правкой.** Планер спрашивает одну запись, прежде чем
  открыть её в редакторе. Сервер старой версии ответил бы 404, и планер
  дождался бы обычного обмена.
- **Конфликты** `read_only` и `deleted` планер превращает в сообщение и вопрос
  пользователю; `restore` он ставит сам.
- **Ссылка общего доступа** доходит до участника как
  `calendar-planner://share?server=<адрес>&token=<токен>` — её собирает
  планер владельца из ответа `/api/share/link`.
- **`/api/ping`** с полем `service` — проверка «это тот сервер» в настройках
  планера; планер меряет и время ответа.

## 11. Ограничения и что можно развить

- TLS — только через обратный прокси.
- Один поток: долгий обмен большого аккаунта задерживает остальные запросы.
  Для домашнего сервера это не заметно; для многих пользователей пришлось бы
  выносить базу в пул потоков.
- Надгробия хранятся вечно: устройство, не появлявшееся год, всё равно должно
  узнать об удалениях. Чистка возможна, если вместе с ней сбрасывать курсоры
  таких устройств.
- Нет журнала аудита — кто и когда изменил запись общего календаря, сервер не
  запоминает (есть только `device` последней версии).
- Приглашение только по ссылке, не по логину — это решение, а не пробел:
  сервер не раскрывает, какие логины у него есть.
